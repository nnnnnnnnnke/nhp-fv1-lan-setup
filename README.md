# PATLITE NHP-FV1 を Mac と LAN 直結で使う

パトライト製ネットワーク監視表示灯 **NHP-FV1**(MP3 再生ネットワーク監視表示灯 NH-FV シリーズ)を、Mac と LAN ケーブル 1 本で直結して設定・制御するための手順メモ。

以下の内容はすべて実機(NHP-FV1、工場出荷時設定)で動作確認済み。

- 確認日: 2026-08-27
- 確認環境: MacBook (Apple Silicon) + macOS Tahoe 26.x + Belkin USB-C LAN アダプタ

## 構成

```
+-----------------------+                      +----------------------+
| Mac                   |                      | PATLITE NHP-FV1      |
|  USB-C LAN アダプタ    |---- LANケーブル ----- |  LANポート            |
|  192.168.10.100/24    |      (直結)          |  192.168.10.1/24     |
|  (手動設定)            |                      |  (工場出荷時)         |
+-----------------------+                      +----------------------+
```

ポイントは 2 つだけ。

1. NHP-FV1 の工場出荷時 IP は **192.168.10.1/24** 固定(DHCP クライアントではない)
2. 直結リンクには DHCP サーバがいないので、**Mac 側に手動で同一セグメントの IP を振る**必要がある(自動のままだと 169.254.x.x のリンクローカルになり届かない)

## Mac 側の設定

USB-C LAN アダプタに手動 IP を設定する(アダプタ名は `networksetup -listallhardwareports` で確認。ここでは "Belkin USB-C LAN")。

```bash
networksetup -setmanual "Belkin USB-C LAN" 192.168.10.100 255.255.255.0
```

IP は 192.168.10.2〜254 の範囲なら何でもよい。ルータ(ゲートウェイ)は不要。
GUI なら「システム設定 → ネットワーク → (アダプタ) → 詳細 → TCP/IP → IPv4 を手入力」で同じことができる。

用が済んで元(DHCP)に戻すときは:

```bash
networksetup -setdhcp "Belkin USB-C LAN"
```

### 疎通確認

```bash
ping -c 3 192.168.10.1
```

```
64 bytes from 192.168.10.1: icmp_seq=0 ttl=64 time=1.625 ms
```

相手が本当に PATLITE かは MAC アドレスの OUI でも確認できる(`80:39:E5` = PATLITE CORPORATION)。

```bash
arp -an | grep 192.168.10.1
```

```
? (192.168.10.1) at 80:39:e5:0:5e:34 on en6 ifscope [ethernet]
```

## アクセス方法

### 1. Web セットアップ画面(HTTP)

ブラウザで **http://192.168.10.1/** を開くと「ＮＨ-ＦＶシリーズ ログイン画面」が出る。

- 初期パスワード: `patlite`

ネットワーク設定、監視設定(Ping/TRAP/アプリ監視)、チャンネル設定、コマンド受信設定などはすべてここから行える。

> [!WARNING]
> 初期パスワードのまま常設ネットワークに繋がない。閉じた直結リンクでの初期設定を終えたら、Web 画面からパスワードと IP を変更すること。

### 2. SNMP(v2c)

エージェント機能が初期状態で有効。リードコミュニティは `public`。

```bash
snmpget -v2c -c public 192.168.10.1 1.3.6.1.2.1.1.5.0
```

```
SNMPv2-MIB::sysName.0 = STRING: nh.patlite.jp
```

PATLITE のエンタープライズ MIB はサブツリー `1.3.6.1.4.1.20440` 以下(`snmpwalk` で確認可能)。SNMP SET(community: `private`)による表示灯制御も実機で動作確認済み — OID と値の意味は「[Zabbix との連携](#zabbix-との連携)」章を参照。TRAP 送受信機能もある。

### 3. ソケット通信 — PNS コマンド(おすすめ)

工場出荷時で **TCP ポート 10000** に PNS コマンド受信が有効になっており、表示灯・ブザー・MP3 チャンネルをバイナリコマンドで直接制御できる。認証はない(だからこそ閉じたネットワークで使うこと)。

コマンド形式: `58H 58H` (製品区分 "XX") + 識別子 + `00H` + データサイズ + データ。

| 識別子 | 内容 |
|---|---|
| `S` (53H) | 表示灯とブザーパターンの制御(データ 6 バイト: 赤/黄/緑/青/白/ブザー) |
| `V` (56H) | MP3 チャンネルの再生・停止(データ 4 バイト) |
| `W` (57H) | 表示灯とチャンネル再生の同時制御(データ 10 バイト) |
| `D` (44H) | デジタル出力制御(データ 1 バイト) |
| `G` (47H) | 表示灯とブザーの状態取得(応答 6 バイト) |
| `C` (43H) | 動作状態クリア(通常状態へ戻す) |

表示灯の値: `00`=消灯 / `01`=点灯 / `02`=点滅1 / `03`=点滅2 / `09`=状態維持。応答は正常 `06H`(ACK) / 異常 `15H`(NAK)。

例:「赤を点灯、他は状態維持、ブザー停止」

```
58 58 53 00 00 06 01 09 09 09 09 00
```

このリポジトリの [pns.py](pns.py) でコマンドラインから叩ける(Python 3 標準ライブラリのみ)。

```bash
./pns.py status          # 状態取得
./pns.py set 100000      # 赤点灯・他消灯・ブザー停止
./pns.py set 020004      # 黄点滅・ブザーパターン4 ※音が鳴る
./pns.py channel 32 -r 3 # MP3チャンネル32を3回再生
./pns.py clear           # 通常状態へ戻す
```

実機での動作確認ログ:

```
$ ./pns.py set 010000
OK (ACK)
$ ./pns.py status
赤: 消灯
黄: 点灯   ← 実際に黄が点灯
緑: 消灯
青: 消灯
白: 消灯
ブザー: 停止
$ ./pns.py clear
OK (ACK)
```

### 4. RSH コマンド

TCP 514 で RSH コマンド(`alert` / `sound` / `stop` / `clear` / `status` / `test` など)も受け付ける。

```bash
rsh 192.168.10.1 -l root alert 100000   # 赤点灯・他消灯・ブザー停止
rsh 192.168.10.1 -l root status
rsh 192.168.10.1 -l root clear
```

`alert` の 6 桁は PNS の `set` と同じ並び(赤黄緑青白 + ブザー 0〜4/9)。

ただし **macOS には rsh クライアントが搭載されていない**うえ、rsh プロトコルは送信元の特権ポート(512〜1023)を要求するため root 権限も必要になる(非特権ポートから接続すると即切断されることを確認済み)。Mac からは PNS コマンド(上記 3)を使うのが素直で、rsh は rsh クライアントのある Linux ホストなどから使う。

## ポートまとめ(工場出荷時・実測)

| ポート | プロトコル | 用途 | 状態 |
|---|---|---|---|
| TCP 80 | HTTP | Web セットアップ画面 | 開 |
| TCP 514 | RSH | rsh コマンド受信 | 開(特権ポート必須) |
| TCP 10000 | PNS | ソケット通信コマンド受信 | 開 |
| UDP 161 | SNMP | GET/SET(community: public) | 応答あり |

## Zabbix との連携

Zabbix と NH-FV シリーズは SNMP だけで双方向に連携できる。デバイス側の追加設定は不要(SNMP 機能が工場出荷時から有効)。

> [!NOTE]
> この README の直結構成のままでは、パトライトに届くのは Mac だけ。Zabbix サーバから使うときは、Web セットアップ画面からパトライトの IP を運用ネットワークに合わせて変更しておくこと。以下のコマンド例は工場出荷時 IP `192.168.10.1` のまま書いているので適宜読み替える。

| パターン | 方向 | 使う機能 | 動作確認 |
|---|---|---|---|
| 1. 障害通知で点灯させる | Zabbix → パトライト | SNMP SET(community: `private`) | デバイス側コマンドを実機確認済み |
| 2. パトライト自体を監視する | Zabbix ← パトライト | SNMP GET(community: `public`) | デバイス側 OID を実機確認済み |
| 3. SNMP TRAP 連携 | 双方向 | TRAP 送受信 | 未検証 |

Zabbix サーバ側の設定は手元に検証環境がないため未検証だが、デバイス側のコマンド・OID はすべて NHP-FV1 実機で動作確認している。

### 1. Zabbix の障害通知でパトライトを点灯させる

#### 最小構成: アクションのリモートコマンド

Zabbix サーバに net-snmp(`snmpset`)があれば、アクションのオペレーション(スクリプト実行)にワンライナーを書くだけでよい。

障害発生時(赤点灯):

```bash
snmpset -v2c -c private 192.168.10.1 1.3.6.1.4.1.20440.4.1.5.1.2.1.2.1 i 2 1.3.6.1.4.1.20440.4.1.5.1.2.1.3.1 i 0
```

復旧時(クリア = 全消灯・監視状態へ復帰):

```bash
snmpset -v2c -c private 192.168.10.1 1.3.6.1.4.1.20440.4.1.5.1.3.0 i 1
```

仕組み: `controlLightControlState`(`...5.1.2.1.2.<index>`)に状態を、`controlLightControlTimer`(`...5.1.2.1.3.<index>`)に `0` をセットすると即時実行される。

- index: `1`=赤 `2`=黄 `3`=緑 `4`=青 `5`=白 `6`=ブザー
- 状態値: `1`=消灯 `2`=点灯 `3`=点滅パターン1 `4`=変化なし `5`=点滅パターン2(**PNS/RSH の 0〜3 と 1 ずれている**ので注意)
- タイマに 1〜99 を入れるとその秒数後に元の状態へ戻る(リストアタイマ)

#### 本格構成: メディアタイプ + [zabbix/patlite_alert.sh](zabbix/patlite_alert.sh)

深刻度に応じて色を変えたい場合はスクリプト型メディアタイプにする。

1. [patlite_alert.sh](zabbix/patlite_alert.sh) を Zabbix サーバの `AlertScriptsPath`(既定 `/usr/lib/zabbix/alertscripts`)に置き、実行権限を付ける
2. メディアタイプを作成: タイプ「スクリプト」、スクリプト名 `patlite_alert.sh`、パラメータは上から `{ALERT.SENDTO}`、`{ALERT.SUBJECT}` の 2 つ
3. 通知先ユーザのメディアに送信先としてパトライトの IP を入れる
4. アクションの通知内容を、障害時は件名 `1:{EVENT.NSEVERITY}`、復旧時は件名 `0:{EVENT.NSEVERITY}` にする(本文は使わない)

スクリプトの深刻度マッピング(スクリプト内の `case` で変更可):

| Zabbix 深刻度 | 動作 |
|---|---|
| 致命的な障害 (5) | 赤 点滅 |
| 重度の障害 (4) | 赤 点灯 |
| 軽度の障害 (3) | 黄 点滅 |
| 警告 (2) | 黄 点灯 |
| 情報 (1) | 緑 点灯 |
| 未分類 (0) | 白 点灯 |
| 復旧 | クリア(全消灯) |

対象色以外の 4 色とブザーは 1 回の SET PDU でまとめて消灯させるので、深刻度が変わっても前の色が残らない。複数障害の優先度制御はしない(最後に届いた通知が勝つ)点だけ注意。

実機での動作確認ログ:

```
$ ./zabbix/patlite_alert.sh 192.168.10.1 "1:4"   # 重度の障害
→ 赤: 点灯
$ ./zabbix/patlite_alert.sh 192.168.10.1 "1:3"   # 軽度の障害に変化
→ 赤: 消灯 / 黄: 点滅1
$ ./zabbix/patlite_alert.sh 192.168.10.1 "0:3"   # 復旧
→ 全消灯
```

### 2. パトライト自体を Zabbix で監視する

パトライトの死活と「いまどの色が上がっているか」を Zabbix 側で持てる。ホストに SNMPv2 インターフェース(community: `public`)を設定し、以下を SNMP エージェントアイテムにする。

| アイテム | OID | 値 |
|---|---|---|
| 表示灯 赤〜白の現在状態 | `1.3.6.1.4.1.20440.4.1.5.1.2.1.4.1` 〜 `.5` | 1=消灯 2=点灯 3=点滅1 5=点滅2 |
| ブザーの現在状態 | `1.3.6.1.4.1.20440.4.1.5.1.2.1.4.6` | 1=停止 2〜6=パターン再生中 |
| ホスト名 | `1.3.6.1.2.1.1.5.0` (sysName) | 例: `nh.patlite.jp` |
| 稼働時間 | `1.3.6.1.2.1.1.3.0` (sysUpTime) | TimeTicks |
| デジタル入力 1〜4 | `1.3.6.1.4.1.20440.4.1.4.4.1.0` 〜 `.4.0` | 0=OFF 1=ON |

このリポジトリの [zabbix/template_patlite_nh-fv.yaml](zabbix/template_patlite_nh-fv.yaml) に上記をまとめたテンプレート(Zabbix 6.0 形式、ICMP ping 監視と「赤が点灯/点滅中」トリガー付き)を置いてある。OID は実機確認済みだが、インポート自体は未検証なのでエラーが出たら報告してほしい。

状態取得の実機確認ログ(SNMP SET で赤を点けた状態):

```
$ snmpget -v2c -c public 192.168.10.1 1.3.6.1.4.1.20440.4.1.5.1.2.1.4.1
SNMPv2-SMI::enterprises.20440.4.1.5.1.2.1.4.1 = INTEGER: 2   ← 2=点灯
```

### 3. SNMP TRAP 連携(未検証)

- **パトライト → Zabbix**: Web 画面の SNMP 設定で TRAP 送信先を Zabbix サーバにすると、CLEAR スイッチ押下(`...20440.4.1.6.4`)や RSH コマンド実行(`...20440.4.1.6.5`)などのイベントが TRAP で飛ぶ。Zabbix 側は snmptrapd + SNMP トラップアイテムで受ける。「誰かが現場でクリアした」を検知できるのが便利どころ。
- **Zabbix → パトライト**: パトライト側の TRAP 受信設定画面に送信元と OID を登録すれば、TRAP 受信をトリガーに点灯・チャンネル再生ができる。Zabbix からは `snmptrap` コマンドをリモートコマンドで叩く形になるが、SNMP SET(方法 1)のほうが設定が少なくて素直。

### FV1 で使えない方法(実測)

- **HTTP コマンド制御(`/api/control?alert=...`)**: NH-FV2 の取説には載っているが、**FV1 実機では 404** だった(FV2 以降の機能)。Zabbix の Webhook メディアタイプで直接叩けるのは FV2 以降のみ。
- **rsh**: Linux の Zabbix サーバからなら `rsh-client` で叩けるが、特権ポート必須・認証なしの古いプロトコルなので、SNMP SET で足りる以上あえて使う理由はない。

## トラブルシューティング

- **アダプタの IP が 169.254.x.x になっている** → Mac 側の手動 IP 設定がされていない。「Mac 側の設定」を参照。
- **IP を変更した後にアクセス先が分からなくなった** → PATLITE 公式の設定ツール「PNS Manager」がネットワーク上の対応機器を検索できる。最終手段は本体の初期化(取説参照)。
- **ping は通るのに Web が開けない** → ブラウザのプロキシ設定を確認。`curl -i http://192.168.10.1/` で切り分け。
